# Использование ИИ-инструментов

Для работы над проектом использовал AI-агента Codex на базе GPT-6.1 Sol.

## Примеры запросов и переданный контекст

Ниже приведены три примера задач, которые я ставил агенту. Формулировки пересказаны, а контекст каждого примера описан отдельно.

### 1. Подготовка mock API для запусков AI-агентов

**Запрос.** Реализовать слой данных для страницы Runs: сохранить заданную модель запуска, подготовить восемь фиксированных записей и настроить MSW для обработки `GET /api/runs`. Добавить сервис `getRuns(): Promise<Run[]>`, который получает данные через `fetch`, обрабатывает HTTP-ошибки и объединяет одновременные вызовы, не кешируя завершённый запрос.

**Переданный контекст.** Агент получил TypeScript-модель `Run` с полями `id`, `name`, `repository`, `branch`, `status`, `createdAt`, `durationSeconds`, `logs` и `result`. Были определены четыре статуса: `queued`, `running`, `succeeded`, `failed`. Для моков требовалось по две записи каждого статуса, ISO-даты с часовым поясом, несколько строк логов, примеры отсутствующих результата и длительности, а также длительность `0`. Для демонстрации загрузки была задана задержка 700 мс, для ошибки - параметр `?mockError=1`: первый запрос возвращает ошибку, повторный выполняется успешно.

**Архитектурные ограничения и результат.** В запросе была закреплена FSD-структура: модель и сервис - в `entities/run`, mock-инфраструктура - в `app/mocks`. Сущность не должна зависеть от моков. MSW требовалось запускать до отрисовки React и сохранять включённым в production-сборке демо. Работу выполняли поэтапно: отдельно согласовывали файлы контракта, fixtures, обработчик, сервис и браузерное подключение. В результате появился источник данных без настоящего бэкенда.

### 2. Реализация интерфейса Runs по требованиям и визуальному ориентиру

**Запрос.** Реализовать англоязычную страницу со списком запусков, состояниями загрузки и drawer подробностей. На этом этапе не добавлять поиск, фильтры и сортировку, но разделить компоненты так, чтобы эти возможности можно было подключить позже.

**Переданный контекст.** Агенту были доступны общий план в `PLAN.md`, архитектурные правила в `AGENTS.md`, существующий сервис `getRuns()` и mock-данные. Дополнительно я передал скриншот таблицы и уточнил, что ориентироваться нужно именно на таблицу, без боковой панели. Визуальные требования включали молочный фон страницы, тёмно-синий контейнер списка, разделители строк и текстовые бейджи статусов. Для таблицы были перечислены поля: название, репозиторий, ветка, статус, дата и длительность.

**Ограничения и результат.** Было задано преобразование таблицы в карточки на узких экранах и полноэкранный drawer на мобильных. В деталях требовались метаданные, логи и необязательный результат, закрытие через Close, Escape и подложку, возврат фокуса и блокировка прокрутки фона. Для проверки поведения я попросил использовать UI-тесты с подменой `getRuns()`, без MSW для Node.js. Агент реализовал страницу, отдельные компоненты списка и состояний, drawer и тесты. Изменения ограничивались заранее согласованными файлами; запуск dev-сервера оставался под моим управлением.

### 3. Поиск, фильтры, сортировка и сохранение состояния в URL

**Запрос.** Добавить поиск по названию и репозиторию, фильтрацию по статусу и обработку нулевой выдачи. Затем я дополнил задачу сортировкой по дате и длительности и сохранением настроек в URL Query Parameters, чтобы они восстанавливались после обновления страницы.

**Переданный контекст.** В проекте уже существовали страница Runs, список, drawer и тестовая среда. Из `PLAN.md` были взяты фильтры All, Queued, Running, Succeeded, Failed. Поиск должен был работать по подстроке, без учёта регистра и пробелов по краям, совместно со статусом. Я рассмотрел вариант с debounce, но выбрал обновление сразу при вводе. Для сортировки были заданы Newest first, Oldest first, Longest duration и Shortest duration; неизвестная длительность должна оставаться в конце, нулевая - учитываться как известная.

**Ограничения и результат.** Поиск, фильтрация и сортировка должны были выполняться локально, без повторных запросов и изменения исходного массива. Для URL были определены параметры `q`, `status`, `sort`, обновление через `replaceState`, обработка `popstate` и сохранение посторонних параметров, включая `mockError`. При отсутствии совпадений требовались сообщение No runs found и кнопка Clear filters, очищающая поиск и статус с сохранением сортировки. Агент добавил панель управления, функции обработки данных, синхронизацию с URL и UI-тесты, включая восстановление состояния после повторного монтирования страницы.

## Неудачные решения ИИ и мои исправления

### 1. Избыточная тестовая инфраструктура

**Что предложил агент.** При настройке тестов агент подключил MSW для Node.js через `setupServer`, добавил проверку HTTP-перехвата и затем назвал отдельные тесты fixtures оставшейся задачей плана. Это расширяло работу вокруг слоя данных, хотя основной фокус задания — поведение frontend-клиента.

**Как я заметил.** Я попросил проверить, есть ли требование тестировать fixtures в `PLAN.md`. Агент подтвердил, что такого требования нет: это была его дополнительная рекомендация. Затем я уточнил, зачем нужен MSW для Node.js, если в UI-тестах можно подменять `getRuns()`.

**Как исправили.** Я исключил отдельные тесты fixtures и попросил оставить среду для frontend-тестирования. Агент удалил Node.js-настройку MSW и тест HTTP-перехвата. Для тестов страницы стали использовать `vi.mock` и управляемые Promise, а браузерный MSW сохранили для работы приложения. Тесты fixtures не создавались, поэтому удалять их не потребовалось. Сам по себе MSW для Node.js не является ошибочным инструментом; лишним было его использование для выбранного объёма тестирования.

### 2. Структура слоя данных без достаточного учёта FSD

**Что предложил агент.** В первоначальном плане агент предложил разместить модель и сервис запусков в `features/runs`, а mock-инфраструктуру — в отдельной папке `src/mocks`. После закрепления FSD такая структура требовала пересмотра: `Run` представляет бизнес-сущность, а не пользовательское действие.

**Как я заметил.** До реализации я спросил, соответствует ли предложенный подход FSD, указанной в `AGENTS.md`. Агент признал, что поведение сервиса подходит, но распределение ответственности по слоям нужно изменить.

**Как исправили.** План скорректировали: типы и сервис разместили в `entities/run`, моки и их подключение — в `app/mocks`. Для сущности определили публичный API через `index.ts`. Исправление произошло на этапе планирования, поэтому перенос уже написанного слоя данных не понадобился.
